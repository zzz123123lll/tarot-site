本册导读 · 顿悟时刻

顿悟时刻:哦,原来 AI Agent 智能体在底层是这么长出“手和脚”的! 看到 Claude Code、OpenAI Codex 或各类智能体(AI Agent)能自己上网查资料、自己连数据库跑 SQL、自 己写代码并根据报错自动修复,很多学习者觉得它像魔法一样不可思议,心里常有一个疑问:“大语言模型明 明只是一个输入文字、输出文字的概率接⻰模型,它到底是怎么伸出手去操作外部软件和执行代码的?” 在进 入八关实操之前,我们先用最透彻的物理拆解把这层窗戶纸捅破。 真相一:大模型自己永远无法直接执行任何工具!Function Calling 的本质是“大脑写申请单,宿 主程序去跑腿” 这是理解一切 AI Agent 最关键的顿悟:无论大模型多么聪明,它的模型权重本体始终运行在一个既不能联 网、也不能读写硬盘的纯数学矩阵沙盒里。 那它是怎么查数据库或改文件的?全靠大模型(LLM)与外围宿主 程序(Host Harness,如你的 Python 脚本、Claude Code 客戶端或 Dify 引擎)之间的一场“四步双簧接力 赛”:

1. 第一棒(递交工具菜单 Schema):宿主程序在向大模型发送你的问题时,顺手在系统上下文里附带了一

份 JSON 格式的《可用工具说明书》(告诉模型:宿主这里有一个叫 execute_sql 的函数,接受字符串参数 query)。

2. 第二棒(模型暂停回答,吐出结构化“调用申请单”):大模型读完问题和菜单,发现需要先查数据,于是

它不生成给用戶看的普通回复,而是输出一段特殊标记的 JSON 文本:{"tool_calls": [{"name": "execute_sql", "arguments": {"query": "SELECT COUNT(*) FROM users"}}]},随后立刻停止生成,挂起等 待。

3. 第三棒(宿主程序真正去跑腿执行):外围的宿主程序捕获到这段 JSON 申请单,由宿主程序在本地电脑或

服务器上真正调用 Python 函数或数据库驱动,拿到真实执行结果 {"count": 15420},再把这个结果包装 成一条 role: "tool" 的观察消息(Observation)追加到对话历史末尾,重新发给大模型。

4. 第四棒(模型看到真实结果,汇总成最终回复):大模型读到宿主塞回来的真实查询结果,这才生成自然语

言呈现给用戶! 看懂这四步接力,你会瞬间明白:所谓 Agent 的“手和脚”,全都是外围宿主程序里的确定性代码;而大模型 的职责,是充当看懂需求、决定调哪个工具、填写什么参数的“认知调度控制器”! 真相二:普通固定流水线(Workflow)与自主智能体(Agent)的分水岭——ReAct 循环与自愈状 态机 如果只是按照写死的顺序依次调用 A 和 B,那叫固定工作流(Workflow);而真正的 Agent 之所以能应对未知 复 杂 任 务 , 是 因 为 它 把 上 述 四 步 接 力 变 成 了 一 个 “ 思 考 ( Thought ) → 行 动 ( Action ) → 观 察 (Observation)→ 反思重规划(Reflection)”的动态 while 循环(ReAct Loop)。当第一次执行代码报错 时,宿主程序不会崩溃退出,而是把红色的错误堆栈(Traceback)原封不动作为 Observation 塞回给模型, 模型在下一轮思考中分析报错原因、修改代码参数并再次发起调用——这就是 Agent 能够自主排错、自我修复 (Self-Healing)的全部底层逻辑! 智能体核心组件 计算机系统工程类比 本册对应攻克的硬核关卡 Tool Schema(工具 契约) 外部硬件设备的驱动程序接口规范(API 签名与类型约束)。 第 1‒2 关:强类型 Pydantic/JSON Schema 声明 + ReAct 思考-行动-观察闭环 控制。 Planner & Memory (规划与记忆) 操作系统的任务调度器(Task Scheduler)与分级缓存(L1/L2 Cache + 磁盘)。 第 3‒4 关:Plan-and-Execute 动态子任务 拆解 + 短期滑动窗口与长期向量记忆分 层。 Actor-Critic 与多智 能体 编译器语法检查器 + 微服务架构下的网 关路由与职责解耦。 第 5‒6 关:Actor-Critic 自动纠错循环 + 中 心化路由(Supervisor)多智能体防死循 环编排。 MCP 协议与安全护栏 USB-C 通用外设总线标准 + 内核态高危 指令拦截防火墙。 第 7‒8 关:MCP 协议标准化挂载 + 只读 SQL 确定性拦截钩子 + 高危操作人工确认 (HITL)。
